## Runtime contract

Cron remains `0 19 * * *` (02:00 Asia/Bangkok). No config/trigger is changed. Normal and seed-free recovery scheduled handlers require D1 backup through BACKUP_DB; a missing binding is an explicit failed job. In Demo/Staging only DEMO_DB/DEMO_BACKUP_DB are mapped; no fallback to Production bindings. Scheduled jobs never fall back to R2, including when the D1 binding is absent. Existing opt-in R2 helpers/status remain separately tested for compatibility; they are not the scheduled backend and are not enabled by this work. Operator must verify both actual D1 identities; runtime binding object inequality is not account/UUID verification.

D1 control requires the existing exact environment row and enabled=1. Missing binding/control/schema or invalid state fails closed; disabled control is explicitly disabled, not success. Scheduled jobs never call readState(), create tables, generate/rotate session keys, seed, initialize or mutate the primary database. Recovery and normal backup use the same validation and job logic. No new HTTP route, restore capability, external notification provider or role permission is introduced. Existing Admin-only backup-status returns a minimized D1 summary when D1 is bound. Sanitized fixed-code logs and backup_control errors report failures; external notifications remain unconfigured.

## Historical schema and compatibility

Git 9ef44d87c6aa87989cc74220de856cc1beae5f52 contains backup_control(id TEXT PRIMARY KEY, enabled INTEGER NOT NULL DEFAULT 1, last_attempt TEXT NOT NULL DEFAULT '', last_error TEXT NOT NULL DEFAULT '') and backup_snapshots(id TEXT PRIMARY KEY, created_at TEXT NOT NULL, source_version INTEGER NOT NULL, payload TEXT NOT NULL, bytes INTEGER NOT NULL). This is historical repository evidence, not source mapping for the deployed binary or proof of the live schema.

Implementation validates the complete non-SQLite-reserved schema, exact known tables/column names/types/PK order using table_xinfo, rejecting hidden/generated columns and incompatible non-ID nullability, and refuses extra tables, views, triggers and non-auto indexes. The exact known _cf_KV DDL is permitted only as a schema object; no key/value/COUNT of it is queried, no generic _cf_ exemption is made, and no existing initialization/read-only reserved-schema policies are modified. Actual cloud target identity/schema still requires separate verification. Missing tables are never created. Schema changes and cloud execution require separate approval.

The payload uses a distinct smart-fleet-d1-snapshot formatVersion=1, not the manual smart-fleet-backup format. Old/current manual restore inspectors reject it rather than silently dropping ledger rows. Existing backup rows are not rewritten or converted. Old scheduled writers must not run concurrently: the historical UPSERT could overwrite a same-day new-format row. Same-day historical/corrupt entries cause failure, not replacement. Operator must plan a cutover with no old/new writer overlap and no same-day format collision; waiting for a verified clean next daily slot is an option, not an automatically approved schedule change.

## Consistent snapshot and integrity

A single bounded SELECT reads all fleet_store id/payload/version rows in binary ID order, including main, environment when present, trip-operation:v1 ledger, known auth/fuel cache and R2 status/lease rows. The snapshot retains exact row payload strings and versions; no historical owner/car/Person ID, audit or credential rewriting occurs. Known auxiliary rows are preserved as opaque strings; this is not permission to execute their content. Unknown row namespaces/schema fail closed instead of being omitted. Source and target use first-primary D1 sessions when supported; no multi-query pagination that could split Fleet and its atomic ledger commit.

The source query refuses datasets over 10,000 rows or 1,600,000 bytes (payload/ID UTF-8 plus per-row allowance) before returning records. The resulting envelope is limited to 1,800,000 UTF-8 bytes, leaving headroom below D1's 2,000,000-byte row limit. JSON escaping can reach the envelope cap earlier. No truncation, ledger omission, compression, chunking or live schema expansion is performed. Capacity refusal preserves existing backups and is a release gate; this is not an unlimited-scale backup solution.

Envelope metadata includes environment, Thai date, createdAt, appVersion, mainVersion and rowCount; SHA-256 covers these and the entire ordered row set. Runtime source Git identity is supplied by the separately reviewed build/artifact manifest, not invented as a snapshot field. Shared account/backup/Trip/Maintenance validators and operation-record reader enforce supported legacy/v3/v4/v5 semantics. Ledger versions must not exceed snapshot main version. SHA-256 detects corruption, not origin or confidentiality. Snapshots contain session/authentication material and personal data and must remain private.

## Publication, retries and retention

Daily ID is YYYY-MM-DD. One conditional INSERT writes a complete envelope only while the existing control is enabled; ON CONFLICT DO NOTHING makes same-day writes immutable. The first valid daily snapshot wins, unlike the historical refreshable same-day backup. Concurrent/retry runs read and validate the stored winner; later main versions are captured on the next day, not silently overwritten into today's copy. Source validity is rechecked even when a daily copy exists.

Read-back checks payload digest, format, semantics, byte count, date/time and source version. The stored daily row is re-read and validated before final status. An older job may accept a newer successful completion only after checking the exact same immutable payload plus enabled control, empty error and a canonical newer completion timestamp not earlier than the snapshot. Corruption, disabled control and newer failure still fail closed; neither daily payload nor newer status is overwritten. A row alone is not complete-job evidence: status requires a successful matching control commit after read-back/retention. Failures retain snapshotSaved separately from overall job completion. No distributed transaction across primary and backup databases is claimed: the source is a coherent point-in-time copy and later app writes continue normally.

Only recognizable transient network/overload/busy errors retry (maximum three attempts, 100/200 ms backoff). Permission, invalid SQL/schema/data and unknown errors fail closed. Each wrapped I/O has a 10-second deadline. D1 binding operations cannot be cancelled by Promise timeout; a late insert can still complete. Immutable IDs/conditional deletes protect data, subsequent runs reconcile, and timeout never claims success. There is no automatic cross-target retry. Failure-status writes may themselves fail; fixed-code logs remain the fallback.

Retention uses the current Thai date plus six prior dates. Stale/next-day/future scheduled events are refused within documented clock tolerance. Purging starts only after verifying a current-day snapshot. Each DELETE is fenced by the unchanged old row, current verified daily payload and enabled control. Current/recent rows are never deletion candidates. Failed upload/read-back means no purge, preserving even an old only-good copy. Retention errors preserve the new snapshot, mark the job failed and can be retried without overwriting it.

Retention captures one upper ID watermark, then uses BINARY-ordered keyset pages of10 rows, advancing past preserved legacy/unknown/corrupt rows. Deleting eligible rows cannot shift an OFFSET, and newly inserted rows beyond the watermark wait until the next job. Cursor order uses UTF-8 bytes to match SQLite BINARY, including Unicode IDs; repeated/non-progressing pages are rejected. Up to100 pages (1,000 candidates) are allowed per invocation. Exceeding this budget is D1_BACKUP_RETENTION_LIMIT with snapshotSaved=true, never success or silently skipped cleanup. Very large preserved backlogs require operator capacity/retention review; provider query/time/CPU limits can fail earlier and are not verified here. Seven days is not a hard storage ceiling for unknown/historical rows. The last verified copy is never expired independently by a lifecycle policy.

## Offline restore and replay

No operational restore API/script is added. Synthetic tests validate the envelope before local writes, restore exact rows into a new isolated SQLite only, check integrity and compare all rows; injected transaction failure rolls back partial local schema/data. Actual normal/recovery Worker checkout/return and same-ID replay/read-only reconciliation are tested against synthetic restored rows, preserving CAS and committed-but-lost-response results without duplicate ledger/trips.

Preserving session keys in an archive is not authorization to revive sessions on a real restore. Real restore/session revocation and any consequences for epoch-bound operation lookup require a separately accepted recovery procedure. Never automatically restore an older D1 snapshot after new writes. Prefer an accepted v5-compatible forward fix that keeps the existing D1.
