## Confirmed defects — not fixed in this documentation task

Both findings below were reproduced against unchanged source with synthetic state and SQLite :memory:, without Worker login, real secrets, cloud calls or persistent database changes. The expected safety behavior fails even though all current automated suites pass; missing assertions explain the gap.

### D1 — Backup inspector accepts invalid trip chronology (P1 / medium data-integrity risk)

Evidence: inspectBackup in [backup.ts](../src/backup.ts) parses trip timestamps and checks odometers/references, but does not enforce end >= start or the same round-trip calendar validation as validateTrip in [fleet.ts](../src/fleet.ts).

Actual probe: synthetic trip start=2026-11-01T10:00, end=2026-11-01T09:00, odoStart=100, odoEnd=110. validateTrip rejects it. A newly checksummed createBackup(sample) envelope is accepted by inspectBackup. Observed: tripValidatorRejects=true, checksummedBackupInspectorAccepts=true.

Impact: “structure/checksum pass” can overstate application validity when an artifact was built from already-invalid data. SHA-256 detects mismatch, not business validity or trusted origin. automaticBackupArtifact/inspectAutomaticBackup reuse this inspector, so the same validation gap can propagate into that chain (source inference; this audit did not perform an additional restore with the malformed artifact). No malicious file or production corruption was observed.

Next: read-only shared semantic validation and regression fixtures for invalid chronology/calendar/bounds; preserve valid legacy/enveloped backups and optional Maintenance fields. Never silently repair, filter, rewrite or restore rejected records. No new web restore/write endpoint.

### D2 — Car initial odometer exceeds Trip's domain (P1 / medium functional/data risk)

Evidence: car action in [api.ts](../src/api.ts) accepts integer initialOdo >= 0 without Trip's 99,999,999 upper limit; App car form has min/step but no matching max. validateTrip rejects odoStart > 99,999,999.

Actual probe: Admin library API with synthetic in-memory SQLite accepted initialOdo=100000000 with HTTP 200, persisted that value; a new trip at that same initial odometer was rejected. Observed: carUpdateStatus=200, savedInitialOdo=100000000, nextTripAtCarInitialOdoRejected=true.

Next: align new/edited car input domain with existing Trip bounds, client + server tests and no-write assertions on rejection. Do not clamp existing cars, alter historical odometers or migrate records. Initial-odometer edits on cars with history also need a separate owner-approved consistency policy; that broader behavior was not proven a regression by this probe.

The first ad hoc probe attempt had a command syntax issue; a corrected attempt hit sandboxed esbuild resolution restrictions. Final permitted local execution completed and produced the observations above. Neither transient probe/tool failure was an application-suite failure.
